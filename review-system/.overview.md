# Review System — L1 Overview

**Purpose:** Automated review collection + sentiment-driven response system for Sharon's US coaching institute. Detects course completion, sends SMS/email review requests, processes replies via Claude, and posts positive reviews to Google Business Profile.

**Status:** Phase 1 complete. Core components implemented and tested locally (mock mode). Ready for platform-specific trigger detection and deployment.

---

## Architecture Layers

```
Trigger (course ends)
    ↓
Message (SMS + email via Twilio/Brevo)
    ↓
Reply (student responds)
    ↓
Claude Processing (sentiment classification + owner-voice response)
    ↓
Action (GBP post if positive, referral ask if positive, thank if neutral/negative)
```

---

## Core Components

### 1. **config.py**
- Loads API keys from `.env`
- Validates required credentials on startup
- Supports mock mode for Twilio and Brevo (for local development without paid credits)

### 2. **twilio_handler.py**
- SMS sending via Twilio (or mock)
- Webhook validation
- SMS reply parsing

### 3. **brevo_handler.py**
- Email sending via Brevo (or mock)
- Email reply parsing (placeholder for production use)

### 4. **claude_conversation.py**
- `process_reply()` classifies sentiment (positive/neutral/negative)
- Generates owner-voice responses
- Routes to appropriate next action (ask referral, thank, acknowledge feedback)

### 5. **gbp_verification_flow.py**
- OAuth redirect to Google sign-in
- Callback handler (auth code → refresh token)
- Encrypts and stores refresh token in Supabase

### 6. **gbp_oauth.py**
- Retrieves recent reviews from GBP location
- Posts replies to existing reviews
- Handles token refresh automatically

### 7. **webhook_router.py**
- Receives SMS replies from Twilio webhook
- Routes to Claude for processing
- Sends Claude's response back via SMS/email

### 8. **trigger_detector.py**
- `BaseTriggerDetector` — abstract base for platform-specific implementations
- `ManualTriggerDetector` — webhook-based manual trigger ingestion
- `enqueue_trigger()` — accepts course-end events

### 9. **main.py**
- FastAPI app with endpoints:
  - `/` — health check
  - `/gbp/auth/start` — redirect to Google OAuth
  - `/gbp/auth/callback` — OAuth callback
  - `/gbp/status` — GBP account status
  - `/webhooks/sms` — Twilio SMS reply webhook
  - `/webhooks/email` — Brevo email reply webhook
  - `/triggers/enqueue` — manual trigger webhook
  - `/triggers/pending` — list pending triggers

## Local Testing (Development)

### Start Server
```bash
cd review-system
pip install -r requirements.txt
python -m uvicorn main:app --reload
```

Access API at: `http://localhost:8000/docs` (Swagger UI)

### Mock Mode
By default, Twilio and Brevo run in mock mode (TWILIO_ACCOUNT_SID == "mock_account_sid", BREVO_API_KEY == "get_from_brevo_settings"). This lets you test the full flow without paid API credits.

## Files & Conventions

- All handlers are singletons (twilio, brevo, etc.)
- All API calls are logged at DEBUG level
- Mock mode returns [MOCK] tagged responses
- Errors are caught and returned as structured JSON
- OAuth state validation uses simple string (can be enhanced to CSRF tokens)

---

## Security Notes

- Refresh tokens are encrypted with Fernet cipher before Supabase storage
- Twilio webhook signatures validated (skipped in mock mode)
- OAuth state parameter prevents basic CSRF
- Never log API keys or phone numbers (debug-level only)

---

## What NOT to Put Here

- Platform-specific trigger detectors (build after discovery)
- Production API keys (use .env)
- Supabase schema definitions (in .abstract.md or a separate schema file)
- n8n workflows (keep in `workflows/` folder with version control)
