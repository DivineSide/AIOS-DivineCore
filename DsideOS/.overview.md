# DsideOS — Content Pipeline Backend

Standalone, deployable backend that exposes the Target Academy content pipeline
as an HTTP API. The product thesis lives here: **the input format is the user's
choice, not a constraint.** Upload a paper as docx / pdf / scanned-pdf / photo;
get back deliverables in the chosen output format + font. Extraction normalises
every input to one **universal Unicode questions JSON**; builders render from it.

This is its OWN stack (own FastAPI + Celery + Redis + Docker Compose + CI/CD),
deployed to the **Hetzner** server — separate from `divinecore-v2`.

```
upload (any format) ─► extract (AI) ─► questions JSON (Unicode) ─► builders ─► docx/pptx/pdf
                                          (the contract)            (font applied here)
```

## Why async (job model)

Extraction + building take 30–90s — past HTTP timeouts. So every working endpoint
returns a `job_id` instantly; the frontend polls and downloads when done.

```
POST /api/extract     upload file              -> job (questions JSON)
POST /api/full        upload file + meta       -> job (all 4 deliverables)
POST /api/build       questions + meta         -> job (paper + deck + key)   [W1]
POST /api/answer-key  questions + meta         -> job (answer-key PDF)        [W3]
POST /api/solutions   questions + meta         -> job (teacher solution)      [W2]
GET  /api/jobs/{id}            poll: QUEUED → RUNNING → DONE/FAILED + manifest
GET  /api/files/{id}/{name}    download an output file
```

**Format setup** (`meta`) is present in every build workflow, per the product
spec: `format` (format-1 | format-2) and `font` (krutidev | unicode) are always
frontend choices. See `api/schemas.py:BuildMeta`.

## Layout

| Path | What it is |
|------|-----------|
| `api/main.py` | FastAPI — upload, dispatch jobs, poll, serve files |

| `docker-compose.prod.yml` | Hetzner: Caddy + api + worker + beat + redis + frontend |

| `DEPLOY.md` | Full Hetzner runbook (DNS, firewall, secrets, first deploy) |
| `.github/workflows/dsideos-ci.yml` | Lives at **repo root** `.github/workflows/` — test → build/push GHCR → SSH deploy |
| `fonts/` | Bundled Kruti Dev 010 + Nirmala UI (.ttf gitignored) |
| `storage/` | Job folders (gitignored — client IP) |

## Deploy (Hetzner CX23, `dsideos.divinesideai.com`)

Push to `main` → GitHub Actions: **test** (compile + font self-tests + import
check) → **build/push** api+worker to GHCR → **deploy** (SSH in, `compose pull`
+ `up -d`) → **notify** `#deploys`. Caddy gets the TLS cert automatically. Full
setup (DNS A-record, firewall ports 80/443/22, the 5 GitHub secrets, server prep)
is in [DEPLOY.md](DEPLOY.md). Frontend ships from its own repo as a separate GHCR
image; Caddy path-splits so they share one origin (no CORS).

## How it imports the pipeline

`pipeline/` and `rag/` live directly inside `DsideOS/` (moved 2026-07-27 — both
were already generic, client-agnostic code, so this was a pure relocation, not
a rewrite). `worker/tasks.py` adds `DsideOS/pipeline/` and `DsideOS/rag/` to
`sys.path` and imports the extractors + builders in place. The Dockerfile's one
`COPY DsideOS/` brings both along automatically.

The genuinely client-specific pieces — `resources/` (front-page.docx etc.) and
`templates/` (logo, watermark) — stay at `clients/target-academy/` as the
source of truth (client IP, gitignored). The pipeline code resolves its own
`BASE` as `DsideOS/` and looks for `resources/`/`templates/` directly under
it, so these get mounted at `DsideOS/resources`/`DsideOS/templates` at
runtime (see `docker-compose.yml`/`docker-compose.prod.yml`) rather than
copied into the image. If DsideOS ever serves a second client, this mount
point becomes the thing that needs a real per-client concept — not yet
built, deliberately deferred until a second client actually exists.

## Input routing (the format-agnostic core)

`worker/tasks.py:_extract_any()` dispatches by extension:
- `.docx` → `extract_docx` (chunked, Unicode out)
- `.pdf`  → `extract_pdf` (auto: digital text vs scanned vision)
- `.png/.jpg/.jpeg/.webp` → `extract_vision` (Claude Vision)

To add an input format, add a branch here — nothing else changes.

## Font handling (the refactor)

Internally everything is **Unicode**. Font is applied ONLY at build time via
`pipeline/krutidev.py:render_runs(text, font)` — a registry switch
(`FONTS = {"krutidev", "unicode"}`). The `font` flows frontend → `meta.font` →
task → `run_pipeline.run(font=...)` → all 5 builders. Adding a font = one row in
the `FONTS` registry. **Never store Kruti Dev bytes internally** — they break
JSON and are lossy; convert to Kruti Dev only at the final render for shipping.

## PDF rendering on the server

`build_answer_key.py` makes a .docx then converts to PDF. On Windows (dev) it
uses Word via win32com; on the server it uses **LibreOffice headless** (`soffice
--convert-to pdf`), installed in the worker image with the Devanagari fonts.

## What NOT to put here

- No frontend — the dashboard is built separately and consumes this API.
- No client outputs in git — `storage/` is gitignored.
- No font binaries in git — `fonts/*.ttf` gitignored (licensed).
- No secrets — `.env` only (gitignored); see `.env.example`.
