How it all fits together

The backend and frontend are completely separate — different repos, different Docker images, different deploys. They communicate only over HTTP. The same domain serves both via Nginx path-splitting on the server.

BROWSER Dashboard (React/Next.js) │ HTTPS requests to dsideos.divinesideai.com ▼ SERVER (Hetzner, 204.168.198.139) Nginx ──── /api/* ──────────▶ FastAPI :8000 └─── /* ──────────▶ Frontend :3000 │ Redis (job queue) │ Celery Worker │ Pipeline scripts → output files

Key point: You never call the backend directly from a hardcoded IP. You call /api/extract — same origin as the frontend. Nginx routes it. This means zero CORS configuration needed.

How a job works end-to-end

The backend is asynchronous — jobs don't block. You submit a file, get a job ID back immediately, poll until done, then download the result.

Upload — POST a file + metadata to /api/extract or /api/full. Response is instant: {"job_id": "abc-123", "status": "QUEUED"}.

Poll — Every 2–3 seconds, GET /api/jobs/abc-123. Status cycles: QUEUED → RUNNING → DONE (or FAILED).

Download — Once DONE, the response includes files: ["paper.docx", "deck.pptx", ...]. Fetch each from /api/files/abc-123/paper.docx.

Downloading a file

// Trigger a browser download once the job is DONE
async function downloadFile(jobId, filename) {
  const res = await fetch(`/api/files/${jobId}/${encodeURIComponent(filename)}`)
  const blob = await res.blob()
  const url = URL.createObjectURL(blob)
  const a = document.createElement('a')
  a.href = url
  a.download = filename
  a.click()
  URL.revokeObjectURL(url)
}

Environment setup

Because the frontend and backend share the same domain, all API calls use a relative path — no base URL needed in production. For local development, proxy /api to the backend.

Next.js — next.config.js

// next.config.js
module.exports = {
  async rewrites() {
    return [{ source: '/api/:path*', destination: 'http://localhost:8000/api/:path*' }]
  }
}

Vite — vite.config.ts

// vite.config.ts
export default {
  server: {
    proxy: { '/api': 'http://localhost:8000' }
  }
}

In production, no proxy needed. The frontend and backend are served from the same domain — Nginx routes /api/* to the backend automatically. Your fetch calls just use /api/... and it works.

Recommended API client

Copy this into lib/api.ts — it handles upload, polling, and download in one place.

// lib/api.ts

export async function submitJob(file: File, meta: {
  paper_name: string
  format?: 'format-1' | 'format-2'
  font?: 'krutidev' | 'unicode'
  generate_explanations?: boolean
}): Promise<string> {
  const form = new FormData()
  form.append('file', file)
  form.append('paper_name', meta.paper_name)
  form.append('format', meta.format ?? 'format-1')
  form.append('font', meta.font ?? 'krutidev')
  form.append('generate_explanations', String(meta.generate_explanations ?? false))

  const res = await fetch('/api/full', { method: 'POST', body: form })
  if (!res.ok) throw new Error(`Submit failed: ${res.status}`)
  const { job_id } = await res.json()
  return job_id
}

export async function pollJob(jobId: string): Promise<{
  status: 'QUEUED' | 'RUNNING' | 'DONE' | 'FAILED'
  files?: string[]
  error?: string
}> {
  const res = await fetch(`/api/jobs/${jobId}`)
  if (!res.ok) throw new Error(`Poll failed: ${res.status}`)
  return res.json()
}

export async function waitForJob(
  jobId: string,
  onProgress?: (status: string) => void,
  intervalMs = 2500
) {
  while (true) {
    const job = await pollJob(jobId)
    onProgress?.(job.status)
    if (job.status === 'DONE') return job
    if (job.status === 'FAILED') throw new Error(job.error ?? 'Job failed')
    await new Promise(r => setTimeout(r, intervalMs))
  }
}

export function downloadFile(jobId: string, filename: string) {
  const a = document.createElement('a')
  a.href = `/api/files/${jobId}/${encodeURIComponent(filename)}`
  a.download = filename
  a.click()
}

Upload + poll pattern (React example)

import { submitJob, waitForJob, downloadFile } from '@/lib/api'

function UploadButton() {
  const [status, setStatus] = useState('')

  async function handleUpload(file: File) {
    setStatus('Uploading...')
    const jobId = await submitJob(file, { paper_name: file.name })

    setStatus('Processing...')
    const job = await waitForJob(jobId, s => setStatus(s))

    // Download all output files
    job.files?.forEach(f => downloadFile(jobId, f))
    setStatus('Done!')
  }

  return (
    <input type="file" onChange={e => handleUpload(e.target.files![0])} />
  )
}

Integration checklist

  • Dev proxy configured (/api → localhost:8000)
  • File upload sends multipart/form-data, not JSON
  • Polling stops on DONE or FAILED — never infinite loops
  • File downloads use the job ID from the response, not a hardcoded path
  • Error states handled: network errors, FAILED status, non-200 responses
  • Max file size: 50 MB (enforced by backend)
  • No auth headers needed right now — backend is open (will add later)

How CI/CD works (backend — for context)

Understanding the backend pipeline helps you set up yours correctly.

TRIGGER git push to main (if DsideOS/ files changed) │ STEP 1 test ── Python compiles, font self-tests, route registration check │ (fails here = nothing deploys) STEP 2 build ── GitHub builds Docker image from Dockerfile push ── Image tagged sha-<commit> pushed to GHCR │ (api + worker run in parallel) STEP 3 deploy ── SSH into Hetzner docker compose pull ← downloads new image docker compose up -d ← replaces containers STEP 4 notify ── Discord #deploys ping with commit + actor

Setting up your frontend CI/CD

The pattern is identical — just swap Python tests for your framework's build/lint step, and the Docker image for your frontend image.

# .github/workflows/frontend-ci.yml
name: Frontend CI/CD
on:
  push:
    branches: [main]
  workflow_dispatch:

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Build and test
        run: |
          npm ci
          npm run build   # or whatever your build command is

      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ghcr.io/divineside/dsideos-frontend:latest

  deploy:
    needs: build-and-push
    runs-on: ubuntu-latest
    steps:
      - uses: appleboy/ssh-action@v1.0.3
        with:
          host: ${{ secrets.HETZNER_HOST }}
          username: ${{ secrets.HETZNER_USER }}
          key: ${{ secrets.HETZNER_SSH_KEY }}
          script: |
            cd /root/DsideOS
            echo "$GHCR_TOKEN" | docker login ghcr.io -u ${{ github.actor }} --password-stdin
            docker compose -f docker-compose.prod.yml pull frontend
            docker compose -f docker-compose.prod.yml up -d frontend
        env:
          GHCR_TOKEN: ${{ secrets.GHCR_PULL_TOKEN }}

DNS + routing on the server

Nginx on the server routes by domain and path. The frontend service runs on port 3000 inside Docker. Once your image is pushed and the frontend service is added back to docker-compose.prod.yml, Nginx routes /* to it automatically — no Nginx config changes needed.

Your Dockerfile just needs to serve the built app on port 3000. For Next.js that's next start -p 3000. For a static build, use a small nginx or serve image.

# Minimal Next.js Dockerfile
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-alpine
WORKDIR /app
COPY --from=builder /app/.next/standalone ./
COPY --from=builder /app/.next/static ./.next/static
COPY --from=builder /app/public ./public
EXPOSE 3000
CMD ["node", "server.js"]

That's everything. Backend is live at https://dsideos.divinesideai.com/api/ — you can start making requests against it today. The waitForJob + downloadFile helpers in lib/api.ts are the main integration surface.
