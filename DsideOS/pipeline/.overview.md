# pipeline/ — content workflow code

The Target Academy content automation, end to end. The whole thing pivots on one
contract: the **universal questions JSON**. Everything upstream produces it;
everything downstream consumes it.

```
ANY input ──► EXTRACTORS ──► questions.json ──► generate_solutions.py ──► run_pipeline.py ──► 4 deliverables
 (docx,         (AI layer)    (the contract)     (AI layer: answers +    (orchestrator)      (builders)
  pdf, photo)                                     explanations)
```

## The contract: universal questions JSON

```jsonc
{
  "filename": "...", "ppt_filename": "...", "solution_filename": "...",
  "answer_key_filename": "...", "title_hindi": "...",
  "format": "format-1" | "format-2",          // paper layout (default format-1)
  "answer_source": "official_key" | null,       // PYQs only — suppresses flags
  "questions": [
    { "n": 1, "stem": "...", "options": ["...","..."], "answer": "a",
      "reason"?: "...", "solution"?: "...", "sources"?: [...], "flag"?: "...",
      "image"?: "crops/..png", "option_images"?: [...] }
  ]
}
```
`run_pipeline.py:validate()` is the gate — required keys, option/answer sanity,
and every referenced crop must exist on disk.

## Input layer (the AI step — non-negotiable for photos/scans)

| Script | Input | How |
|--------|-------|-----|
| `extract_docx.py`   | any `.docx` paper | flatten text (run-verbatim, legacy font safe) → Claude → JSON. Exposes `extract_from_text()` (shared text path). |
| `extract_pdf.py`    | any `.pdf` | **auto-detects** digital vs scanned: text layer → `extract_docx.extract_from_text`; image-only → vision. Self-corrects (text path fails over to vision if empty). |
| `extract_vision.py` | photos / image inputs | render via fitz @150dpi → Claude **Vision** → JSON |
| `llm.py`            | — | shared Anthropic client, `.env` key load, `parse_json` |

## Solution generation (AI step — runs between extraction and pipeline)

| Script | Mode | What it does |
|--------|------|--------------|
| `generate_solutions.py` | **EXPLAIN** (if `answer_source: "official_key"`) | Answer already known — generates विस्तृत व्याख्या proving why it's correct. |
| `generate_solutions.py` | **FIND+EXPLAIN** (no official key) | Independently finds the correct answer via web search, then explains it. Flags low-confidence answers for Mayank review. |

Both modes write `q["solution"]` and are re-runnable (skips questions already done).
`--batch N` limits to N questions per run; `--only 1,5,12` targets specific questions.

## Input extractors (AI step — non-negotiable for photos/scans)

These replace the one-off `extract_set49.py` (hardcoded to one file's markers).
`extract_docx` keeps legacy Kruti-Dev bytes verbatim (builders re-apply the
font); `extract_vision` emits real Unicode (photos are real Unicode).
**Answers are only filled if the source prints a key.** Either way, run
`generate_solutions.py` next to populate `q["solution"]` before the pipeline.

> Note: the live API call needs outbound HTTPS to api.anthropic.com. Per the
> locked doctrine, generation runs on Claude Code plan usage for now; the
> metered API key is the productization path. The extractor request/parse path
> is unit-tested; only the network leg is environment-gated.

## Builders (deterministic — never change, client IP)

| Script | Output |
|--------|--------|
| `build_deck.py`         | `(Class).pptx` — verbatim MCQs, NO answers |
| `build_solution.py`     | `- Solution (Teacher).docx` — answers + reason + ⚠ flags + sources (HERE ONLY) |
| `build_paper.py`        | `.docx` — **format-1**: branded 2-col paper + उत्तरमाला key |
| `build_paper_format2.py`| `.docx` — **format-2**: per-question 8-row tables, options pre-marked "incorrect" |
| `build_answer_key.py`   | `- Answer Key.pdf` — one-page grid |
| `build_poster.py`       | marketing `.png` |

**Format selection:** top-level `"format"` in the JSON. `run_pipeline.py` branches
the paper builder on it; format-2 replaces the format-1 paper, deck/solution/
answer-key are unchanged. Both share the `unicode_to_krutidev_runs` text path
(Hindi → Kruti Dev 010, English → Times New Roman).

## Font handling (Unicode-internal, font-at-build)

**Everything internal is Unicode.** Extraction emits Unicode Devanagari; the JSON
stores Unicode; Kruti Dev bytes are NEVER stored (they break JSON and are lossy).
The font is applied ONLY at build time via `krutidev.py:render_runs(text, font)`
— a registry switch (`FONTS = {"krutidev": Kruti Dev 010, "unicode": Nirmala UI}`).
Every builder takes a `font=` param; `run_pipeline.run(font=...)` threads the
frontend's choice through all five. Adding a font = one row in the `FONTS`
registry — no builder edits. Default stays `"krutidev"` (shipping behavior).

## Deployed as a backend

This pipeline is wrapped as a standalone API in **`DsideOS/`** (FastAPI + Celery +
Redis, deployed to Hetzner) — see [DsideOS/.overview.md](../../../DsideOS/.overview.md).
The backend imports these scripts in place; `_docx_to_pdf` uses LibreOffice
headless on the server (win32com/Word on Windows dev).

## Support

`krutidev.py` (Unicode↔Kruti Dev bidirectional + `render_runs` font switch),
`crop_figure.py` (diagram crops),
`ingest.py` (corpus build), `fetch_questions.py`/`scrape.py`/`search.py` (sourcing),
`extract.py` (agentic answer extraction), `inspect_*.py` (template reverse-eng).
